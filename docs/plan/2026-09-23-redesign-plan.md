# תכנון מחדש — לקט (halacha-sources)

תאריך: 2026-09-23 (עודכן 2026-09-24 אחרי ההחלטות) · סטטוס: **החלטות התקבלו** (סעיף 8) — שום קוד לא שונה עדיין.

המסמך הזה עונה על ארבע שאלות:
1. מה המטרה של הפרויקט, ומה המטרה של כל חלק בו.
2. מה להוריד — מה לא רלוונטי, כפול או מת.
3. איך להפוך את מה שנשאר למדויק יותר.
4. איך משתמש עובד עם המערכת — כולל עבודה עם Claude, שכרגע היא מקומית בלבד.

בסוף: תוכנית עבודה בשלבים, שלד ה-README החדש, ורשימת החלטות שמחכות לך.

## 1. המטרה, במשפט אחד

> **לקט הוא כלי לימוד אישי שבונה "דף מקורות" מדויק לכל סימן בשולחן ערוך:** מהטור והבית יוסף — אל המקורות שהם מביאים (גמרא, רמב"ם, ראשונים, מדרש, תנ"ך) עם המפרשים שלהם — ועד תמצית הלכה למעשה לפי סעיפי השו"ע. הדף ניתן להדפסה, לייצוא ולאיסוף לקבצי לימוד.

מבחן לכל פיצ'ר: **האם הוא עוזר ללמוד סימן ולבנות עליו דף מקורות נכון?** אם לא — הוא יוצא או מוקפא.

זה מה שהנתונים מראים שבאמת קורה (DB מקומי, `data/annotations.db`):

| מה | כמות | משמעות |
|---|---|---|
| דפי מקורות עם תוכן אמיתי | 1 (או"ח א, 18 פריטים) + 1 קטן (או"ח תרכה) | הליבה בשימוש: מב"י → גמרא + הסברים + כותרות |
| משתמשים | 2 (admin + user) | בפועל משתמש אחד |
| קבוצות / הזמנות / בקשות הצטרפות | 1 / 1 / 1 | נתוני בדיקה |
| ניתוחי סעיף (AI) | 1 | הפיצ'ר חדש, עוד לא בשימוש |
| קבצי לימוד | 5 (27 סימנים) | בשימוש ניסיוני |

והאתר המפורסם (`halacha.lazari.site`) לא עונה — ה-deploy בפועל מת.

## 3. החלטות ארכיטקטורה מוצעות

### 3.1 מקומי, משתמש יחיד
- השרת מאזין רק ל-`127.0.0.1`. אין התחברות, אין משתמשים, אין קבוצות.
- טבלת `users` מצטמצמת ל"פרופיל מקומי" יחיד; מפתח `user_id` נשאר בטבלאות כדי שלא ייסגר הפתח לריבוי משתמשים בעתיד.
- **למה:** ~1,600 שורות של ניהול משתמשים, הרשאות ומודרציה משרתות תרחיש שלא קיים, מסבכות כל route (בדיקות session) ומוסיפות באגים — למשל `userName: currentUser` בהדגשות מגיע עדיין מ-localStorage (`"anonymous"`) ולא מה-session.
- **הוחלט:** כל קוד ריבוי המשתמשים נשמר בענף `archive/multi-user` (נוצר מ-main לפני ההסרה), כך שאפשר להחזיר אותו אם השרת יחזור לפעול.
- אם שיתוף יחזור — כדאי לשקול שכבה נפרדת (ייצוא/קישור לקריאה) לפני שמחזירים multi-tenant מלא.

### 3.2 מנגנון AI אחד: Claude המקומי
היום יש **שלושה** מנגנונים שונים:
1. SDK בתשלום (`/api/agents/[id]/run`) — לא בשימוש.
2. סקיל `siman-points` — Claude Code מתחבר לאפליקציה, מייצר ושומר דרך `/api/agents/[id]/save`.
3. `claude -p` מתוך השרת (`lib/claudeCli.ts`) — לניתוח סעיף/קטע.

המוצע: **מנגנון אחד — `lib/claudeCli.ts`**, ושתי דרכי הפעלה שכותבות לאותן טבלאות:
- **מהממשק:** כפתור ✨ → השרת מריץ `claude -p` עם JSON schema → נשמר.
- **מ-Claude Code:** סקיל שמריץ את אותו ניתוח (שימושי לריצה על הרבה סימנים, או כשרוצים לשוחח על התוצאה לפני השמירה).

להסיר את `@anthropic-ai/sdk`, את `anthropicClient.ts` ואת route ה-`run`.

**הוחלט — מה נשאר מה-AI:** רק **ניתוח הסעיף** (סיכום + נקודות מעשיות בתצוגה "לפי סעיפי שו"ע"). ניתוח הקטע הבודד והסוכן "תובנות טכנולוגיות" יורדים. אם גם הסוכן "נקודות הלכה למעשה" יורד (סעיף 8), כל מנגנון הסוכנים יורד: עמוד `/agents`, טבלת `agent_definitions`, `/api/agents/*` והסקיל `siman-points`. במקומו יבוא סקיל שמריץ את ניתוח הסעיף מ-Claude Code.

### 3.3 מקור אמת אחד לדף: `documents`
היום כל מקור שנמשך נשמר **פעמיים**: כ-excerpt בדף (לפי משתמש) וכ-annotation (גלובלי, עם סטטוס מודרציה), רק כדי לצבוע את הטקסט בפאנל. בגלל זה יש בקוד לוגיקת סנכרון ו"מילוי חוסרים" (`page.tsx` ~שורות 289–352) למקרים שבהם השניים לא תואמים.

המוצע: להוסיף ל-`Excerpt` את השדה `highlightText`, ולגזור את ההדגשות בפאנל ישירות מהדף. אחרי מיגרציה — טבלת `annotations` יורדת, וכך גם מצב `quantity` בקבצי לימוד (או שמחשבים אותו מהדפים).

### 3.4 Claude Code כ"ממשק שני" — מתועד ובתוך הריפו
- סקילים שקשורים לפרויקט עוברים ל-`.claude/skills/` **בתוך הריפו**, כדי שיהיו מנוהלים בגרסאות יחד עם ה-API שהם קוראים לו. היום `siman-points` יושב ב-`~/.claude/skills` ומתעד endpoint של התחברות שעומד לרדת.
- בלי התחברות אין צורך בזרימת ה-CSRF/cookie/Keychain של הסקיל — רק `curl localhost:3000`.

## 4. דיוק — איפה המערכת יכולה לטעות היום, ומה עושים

### 4.1 זיהוי מקורות (הליבה) — אין אף בדיקה
- שני מזהים נפרדים: `parser.ts` (רץ על טקסט שלם) ו-`detectSourceRef.ts` (רץ על סימון), כל אחד עם מפות ידניות משלו (`rambamMap`, `rishonimMap`, `midrashMap`, `tanakhBooks`, `lastChapterMap`).
- היסטוריית ה-git מלאה בתיקוני זיהוי נקודתיים (ר"פ, מהל', "הרמב"ם" סתם, כפילות ירושלמי/משנה, revert…) — סימן מובהק שחסרה רשת ביטחון.

**מה עושים:**
1. **מאגר דוגמאות אמת (golden set):** קובץ JSON של `{טקסט, ref צפוי}` — מתחילים מכל המקורות שכבר נמשכו ב-או"ח א ומכל באג זיהוי שתוקן ב-git log. להוסיף `vitest` ולהריץ `npm test`.
2. **מזהה אחד** עם API אחד, `detect(text) → {ref, confidence, span}[]`, שבו `parser` ו-`detectSourceRef` הופכים לשכבות פנימיות.
3. **ציון ודאות גלוי בממשק:** זיהוי חלקי (למשל מסכת בלי דף) מסומן, והמשתמש מאשר ידנית — ולא נכנס לדף בשקט.

### 4.2 מיפוי מפרשים לסעיפים — היוריסטיקה שלא מתריעה על טעות
`buildSeifBlocks` מחלק את הערות המפרש לסעיפים לפי **ספירת קישורים** מספריא (סמן רץ). אם קישור אחד חסר בספריא, כל ההערות שאחריו זזות סעיף אחד — בלי שום התראה.

**מה עושים:**
1. **בדיקת עקביות:** סכום הקישורים למפרש צריך להיות שווה למספר ההערות שלו בסימן. אם לא — הבלוק מסומן "⚠️ מיפוי לא ודאי" בממשק, וניתוח ה-AI שלו לא נשמר בלי אישור.
2. **בדיקת דגימה:** סקריפט שעובר על כ-20 סימנים מכל ארבעת החלקים ומדווח על אי-התאמות. זה מראה אם מדובר במקרה קצה או בבעיה רחבה.

### 4.3 AI — תוכן בלי עוגן
- שלושה פרומפטים שונים ל"הלכה למעשה" עם כללים שונים: הסוכן מחייב ציון מקור בסוגריים; ניתוח הסעיף מחייב "אל תמציא" אבל לא ציון מקור.
- הסוכן "תובנות טכנולוגיות ויישומיות" מייצר רעיונות, לא הלכה, ונשמר **בתוך דף המקורות** לצד מקורות אמיתיים.

**מה עושים:**
1. **פרומפט בסיס אחד** עם כללים קשיחים (לא להמציא, לציין מחלוקת, **כל נקודה עם `source`** מתוך רשימה סגורה של תוויות המקורות שנשלחו). סוכנים מותאמים מוסיפים הנחיות על גבי הבסיס — לא במקומו.
2. **וולידציה בשרת:** נקודה שה-`source` שלה לא נמצא בקלט נדחית או מסומנת.
3. **מקור ושקיפות:** לכל ניתוח נשמרים מודל, תאריך ו-hash של הקלט, ובממשק הוא מוצג כ"ניתוח AI" בעיצוב שונה ממקור.
4. תוכן לא-הלכתי (כמו תובנות טכנולוגיות) — לא בדף המקורות המודפס כברירת מחדל. זו החלטה שלך (סעיף 8).

### 4.4 נתונים ומטמון
- `sectionIndex` נשמר לפעמים כמחרוזת (`"2"`) ולפעמים כמספר — לנרמל במיגרציה.
- המטמון של ספריא (`cache/sefaria`) לא פג לעולם, כך שתיקונים שנעשים בספריא לא מגיעים. להוסיף כפתור "רענן טקסטים" לסימן, ולשמור ב-`documents` את גרסת הטקסט שממנה נמשך כל מקור.
- מיגרציות סכמה רצות בתוך `getDb()` בכל עליית שרת. לפני שמורידים טבלאות — גיבוי אוטומטי של `annotations.db`.

## 5. איך המשתמש עובד עם המערכת (תהליך היעד)

```
הפעלה  →  בחירת סימן  →  לימוד (פאנלים / לפי סעיפים)
          ↓
סימון טקסט בב"י/טור  →  "הגדר מקור"  →  זיהוי + אישור נוסח + בחירת מפרשים  →  נכנס לדף
          ↓
הוספת הסבר / שאלה-תשובה / כותרת / תמונה  ·  קישור לסעיף  ·  הסתרה מהדף הסופי
          ↓
✨ ניתוח סעיף (מהממשק, או "תנתח את סימן א" ב-Claude Code)
          ↓
דף מקורות  →  PDF / Word / הדפסה     ·     קובץ לימוד  →  ייצוא מאוחד
```

### הפעלה (יעד)
```bash
cd ~/side_projects/halacha-sources
npm run local        # nvm use 20 + next dev -H 127.0.0.1, פותח את הדפדפן
```
דרישות: Node 20 (היום ה-CLAUDE.md אומר 18.20.1 והסקיל של ה-deploy אומר 20 — לאחד ל-20, עם `.nvmrc`), ו-`claude` CLI מחובר (בשביל ה-AI).

### עבודה עם Claude Code (מקומית)
| רוצה… | אומרים ל-Claude Code | מה קורה |
|---|---|---|
| להריץ את האפליקציה | "תפעיל את לקט" | `npm run local` ברקע |
| לנתח סימן שלם | "תנתח את סימן א באו"ח" | עובר על כל הסעיפים, מדלג על מה שעדכני (hash), שומר |
| להריץ פרומפט מותאם | "תריץ את 'נקודות הלכה למעשה' על סימן ה" | אותה פעולה, לסוכן אחד |
| לבדוק זיהוי מקורות | "תבדוק את הזיהוי בסימן כה" | מריץ את המזהה על הב"י ומדווח מה זוהה ומה לא |
| גיבוי | "תגבה את לקט" | מעתיק את ה-DB וקבצי JSON לתיקיית גיבוי עם תאריך |

**מגבלה ידועה:** ה-AI עובד רק כשהשרת רץ על המחשב שלך, עם `claude` מחובר. זה מכוון: בלי מפתח API ובלי עלות נוספת.
